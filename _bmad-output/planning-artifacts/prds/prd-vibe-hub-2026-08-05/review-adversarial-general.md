# Adversarial Review — PRD: Vibe Hub (prd-vibe-hub-2026-08-05)

Reviewer stance: cynical architect/UX lead about to build from this document. Findings below are things that would cause real confusion, rework, or a blocked build if uncaught — not prose nits.

---

- **FR-1's launch gate is logically impossible as written.** The Landing Page Consequences (§4.1) require "real screenshots/testimonials, not placeholder assets... before rollout." But this is the *first* rollout of a never-shipped internal tool — there is no prior usage to generate real testimonials or social proof from. As written, FR-1 cannot be satisfied before the very event (rollout) it's gating. Either the requirement needs a different bar for a v1 internal audience (e.g., "team roadmap/credibility framing" instead of testimonials), or the PRD needs to admit this gate is unsatisfiable at first launch and say what substitutes for it.

- **Course Progress (FR-3) status inside MVP scope is self-contradictory.** §4.2 presents FR-3 as a numbered, in-scope Functional Requirement realizing UJ-1-adjacent value. Its own Notes say it's "sequenced after authentication," and §6.2 Out of Scope explicitly defers authentication entirely for MVP. §6.1 In Scope, meanwhile, doesn't mention course progress at all. So: is FR-3 in MVP or not? As written, a builder cannot tell whether to build a "session-local or team-wide placeholder" (the Notes' own fallback suggestion) or skip the feature outright. This needs one explicit line in §6.1/§6.2, not an inference left to the reader.

- **FR-9 (waitlist visibility) has the same in/out-of-scope ambiguity, compounded by an open question that undercuts the FR's premise.** FR-9 is written as a firm requirement ("Léandro... can see aggregated waitlist signal"), but §6.1 In Scope never lists a waitlist-count view, and Open Question 6 literally asks "Does an admin view for waitlist counts already exist, or does it need to be built?" A PRD section cannot assert a capability as a testable requirement while a live open question asks whether it currently exists at all — that's not a spec, it's a placeholder wearing a requirement's clothes.

- **Rollout-readiness and the auth deferral contradict each other.** §1 states this PRD "describes the product as it should be when it's ready for that first real rollout." §6.2 defers authentication entirely. But FR-4's Notes and Open Question 5 both flag that the Admin surface has *zero* access control and ask whether that's acceptable "before real designers (and thus a discoverable `/admin` path) are in the picture." The PRD never resolves this — it just restates the tension in three different places (§4.2 FR-4 Notes, §8 Privacy, §9 OQ-5) without picking a side. A builder following §6.1/§6.2 literally would ship an open `/admin` write path into the same rollout §1 calls "ready."

- **Non-Goals vs. FR-6 is unreconciled scope creep.** §5 Non-Goals states Vibe Hub "is not becoming a general-purpose AI chat product." FR-6 then requires slash commands *and* named-project organization of conversations — both of which are exactly the differentiating chrome of general-purpose chat products (ChatGPT/Claude-style project organization). The PRD never explains why these specific general-chat-product features are exempt from the Non-Goal, leaving it to the builder's judgment where the line is — which is precisely the kind of ambiguity a Non-Goals section exists to prevent.

- **Prompt hand-off mechanism is inconsistently specified.** The Glossary (§3) and UJ-1 both describe hand-off as the user manually copying the assistant's prompt and pasting it into UI Builder. FR-7's Consequences, however, require "a prompt handed off from the IA tab (FR-5) works in UI Builder without manual reformatting by the user" — phrasing close enough to "automatic hand-off" that a builder could reasonably implement either a manual-copy flow or a one-click auto-fill and claim compliance. Given hand-off is called out as the product's core differentiator (§1, OQ-10), this ambiguity is not cosmetic.

- **FR-9's acceptance criterion doesn't actually constrain anything.** "Per-tool waitlist counts are viewable somewhere (Admin surface or direct data access) without querying the database by hand" is nearly unfalsifiable: "direct data access" (e.g., opening the Supabase table editor) *is* querying the database by hand for most practical definitions. This "consequence" would be satisfied by doing nothing beyond what already exists, which defeats the purpose of writing a testable consequence at all.

- **Waitlist capture has no defined identity model, but downstream claims assume one.** FR-8 says interest is "recorded per-tool in Supabase, distinguishable by which tool," but never specifies what identifies the person joining (no auth exists per §6.2). UJ-3's climax and the team-lead JTBD (§2.1, tagged `[ASSUMPTION]`) both imply someone can look at waitlist data and draw conclusions about *who* wants what — but with no user identity captured, the data may be nothing but anonymous per-tool counters, which cannot support any "which designer wants X" use case. The PRD doesn't say whether that's acceptable or a gap.

- **"Effective August 2026" EU AI Act obligation may already be due, not upcoming.** §4.3 and §8 both flag the EU AI Act transparency requirement as "effective Aug 2026" and ask the reader to "verify before rollout" as if it's a future deadline. The PRD itself is dated 2026-08-05. This is written as a forward-looking heads-up when, on the document's own timeline, it may already be a present-tense compliance gap — worth a factual check rather than a deferred note.

- **§8 Privacy statement asserts limited exposure as settled fact without support.** "No user accounts exist yet, which limits exposure today" glosses over the fact that Supabase already stores course data and waitlist entries (§0, §4.2, §4.4) — i.e., the backend is already live and already collecting *something*, whether or not it's tied to a named user. The claim that current exposure is low is asserted, not demonstrated (no data-flow or PII inventory is given), which is a meaningful gap for a document that explicitly puts GDPR in scope one sentence later.

- **Cost/rate-limiting risk is called "currently low" while the primary success metric explicitly drives usage of the metered API.** §8 says Gemini cost risk is low "given internal-only, small-team usage" (tagged `[ASSUMPTION]`), but SM-1 — the PRD's *primary* metric — is defined as maximizing IA → UI Builder hand-off completions, i.e., deliberately driving traffic to the metered endpoints this same section calls low-risk. No rate limit or budget ceiling is specified anywhere in scope, so if SM-1 succeeds, the "low risk" assumption is the first thing invalidated by the PRD's own goals.

- **FR-6's testable consequence is trivially satisfiable and proves nothing about the actual requirement.** "At least one slash command is available and documented... (e.g., via a `/help` or autocomplete affordance)" can be satisfied by a single stub command with no real utility, while the FR's prose promises a general slash-command *capability*. The "e.g." makes even the documentation channel optional/illustrative rather than mandated, so this consequence doesn't actually pin down what a reviewer should check for at acceptance time.

- **Glossary's "Workspace" definition contradicts the auth deferral.** §3 defines Workspace as "the authenticated-or-not application shell," implying auth-gating is a live design axis. §6.2 flatly defers authentication out of MVP scope entirely. The glossary term should not hedge on something the scope section has already decided — as written it reads like two different drafts were never reconciled.

---

**Cross-cutting observation:** a large share of these issues trace back to the same root pattern — a capability is asserted as an in-scope, testable FR in §4, then immediately hedged, deferred, or contradicted in its own Notes/§6/§9. That pattern (FR-3, FR-4's access control, FR-9, FR-1's social-proof gate) suggests the PRD's numbering and scope sections were drafted somewhat independently and never cross-checked against each other. Before this is treated as build-ready, every FR should be traceable to exactly one of: "ships in MVP as specified," "ships in reduced/placeholder form because X is deferred," or "not in MVP, tracked as vNext" — right now several FRs are all three at once, depending on which section you read.
